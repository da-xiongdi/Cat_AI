# Cat_AI 工作台建设与管理方案

版本 v0.3，修订日期为 2026-11-18（Asia/Shanghai）。WB-13 的部署与父任务验收见[交付记录](../workbench/wb13.md)。

本文规定工作台应提供的能力、信息组织和管理规则。本轮开发步骤、交付物及验收场景见[增量实施计划](../workbench/management_improvement_plan.md)。此前的模块扩展设计与历史排期保存在[v0.2 方案](project_workbench_plan_v0.2.md)，原交付记录继续有效。

## 1. 目标、范围与文档职责

工作台应让使用者快速回答：项目总体路线是什么、当前工作处于哪里、下一步有哪些具备条件的任务、应依据哪份计划实施、已有交付能否追溯到验收证据。

本轮重点是管理能力：任务分类、研发路线展示、近期工作编排、执行计划关联、文档组织和成果追溯。沿用 FastAPI、Jinja2、HTML/CSS 与 SQLite，不重建已有任务、索引、验收及预测队列。

将以下三类内容分别维护：

| 内容 | 回答的问题 | 维护位置 |
|---|---|---|
| 工作台建设方案 | 工作台提供什么能力，遵循什么规则 | 本文 |
| 工作台实施计划 | 本轮如何开发、依赖什么、如何验收 | `docs/workbench/management_improvement_plan.md`；交付后增加 WB 记录 |
| 具体科研任务及计划 | 科研做什么、采用什么技术、取得什么结果 | 任务管理库、[总体设计](system_design.md)、专项方案和对应执行计划 |

本文不安排 S2/S3 等科研工作的优先顺序，不重新设计 A–F 路线，不以工作台开发推动科研任务状态变化。本轮不训练模型、不改科研数据库及既有科研产物，不调整历史科研验收结论。

## 3. 两类任务与页面组织

### 3.1 分类规则

科研任务与工作台建设任务共用同一管理库、任务服务和验收机制，通过明确类别分开组织。

| 维度 | 科研任务 | 工作台建设任务 |
|---|---|---|
| 管理目标 | 数据、特征、模型、筛选、实验等研发交付 | 工作台页面、服务、接口、迁移与运维能力交付 |
| 编号 | 保留现有任务 ID | 保留 WB 系列编号，新编号核查后分配 |
| 路线归属 | 关联科研路线节点与既有阶段/里程碑 | 归入工作台建设工作包，不强制挂入 A–F 主线 |
| 执行计划 | 对应科研专项执行计划 | 对应工作台实施计划 |
| 验收 | 按任务范围核对工程或科研证据 | 核对功能、兼容性、数据隔离及交互 |

类别由任务实际交付目标确定，编号仅辅助历史分类。为训练服务开发工作台操作入口属于 WB 任务；开发训练算法、运行科研实验属于科研任务。二者可显式建立依赖，不合并为一个任务。

历史数据迁移只增加分类与关联，不重建 ID、不重置状态、不补造验收。无法判断类别时列入待核对清单，核对前不计入任一类别的完成统计。

### 3.2 页面职责与默认范围

保留“项目管理、数据基础、智能研发、实验闭环”四组导航。在项目管理组补充路线图与下一步工作，并提供独立的“工作台维护”入口。维护入口复用任务、文档及成果页面的分类视图。

| 页面/入口 | 职责 | 默认范围 |
|---|---|---|
| 项目总览 | 总体目标、当前焦点、近期任务、关键问题及证据摘要 | 科研；工作台状态单列摘要 |
| 总体研发路线图 | 展示研发阶段、研究方向及任务位置 | 科研，不混入 WB 节点 |
| 下一步工作 | 展示近期安排、依赖及项目计划章节入口 | 科研；可显式切换到工作台建设 |
| 阶段任务与问题 | 任务编辑、依赖、检查项、问题及决策 | 科研；可切换类别或查看全部 |
| 资料与技术方案 | 按用途查阅文档及关联任务 | 科研/系统文档；建设文档独立分类 |
| 成果与验收 | 固定交付版本、验收结论及证据有效性 | 随当前任务类别筛选 |
| 工作台维护 | 建设工作包、WB 待办、建设计划、交付及备份恢复 | 工作台建设 |

范围切换显示在页面标题、筛选条件和统计说明中，并保存在 URL。跨页面导航尽量保持类别；确需跨类别跳转时显示目标类别。查看全部时两类分别计数，不用混合完成率代表科研进度。现有对象 URL 保持可用。

## 4. 核心功能要求

### 4.1 项目总览

默认首页按“项目目标与阶段 → 当前焦点 → 路线简图 → 近期工作 → 问题与成果”组织。展示当前任务、下一步入口、近期完成项、待决策事项及最近活动。工作台建设摘要独立展示，进入维护视图查看详细排期。

所有数字附类别、统计范围、数据来源和观察时间。样本的测试记录数与材料数分别显示，任务完成数与科研证据分类分别显示；未接入显示“待接入”，成功查询为空才显示 0。不以任务数量比例推算整个科研项目完成百分比。

### 4.2 总体研发路线图

沿用总体设计中的 A–F 阶段，以横向主干加多级树状分支展示研究方向与任务。阶段名称及顺序从现有路线核对登记；研究分支来自已有方案与任务，缺少拆分时显示“尚未拆分”，不自动编造科研任务。

路线区分三种关系：节点父子关系表达研究结构，节点与任务关联表达实施归属，任务依赖表达执行前提。父子关系不自动生成依赖，A–F 排列也不表示相邻阶段全部互为前置条件。

一个任务只有一个主归属节点，其他节点通过引用展示；跨节点统计按任务 ID 去重。路线节点只显示名称、状态摘要和必要标识，方案、实施步骤、成果及验收细节由详情页承接。

默认展示主干与一级分支，支持逐级展开/折叠、缩放、平移、全屏、适应屏幕、全部展开/收起、恢复初始视图，以及当前焦点定位和任务详情反向定位。展开操作与打开详情提供不同入口。模型不限制固定层数；大量节点按需加载，提供树形列表作为补充入口。拖动画布只改变视图，修改节点归属必须显式保存并记录历史。

节点不复用任务状态机。摘要优先显示“受阻、推进中、待验收”等实际情况，并附已完成/已纳入任务数；全部已取消或未关联任务时不得标为完成。有未拆分分支时标为“范围待补充”；只有已确认范围内全部有效任务通过验收且证据可用时才显示“已纳入范围完成”。这些规则属于新增视图逻辑，不能反写任务状态或宣称研究方向整体完成。

### 4.3 下一步工作与计划关联

“下一步工作”是现有任务的筛选与编排视图，不建立另一份待办数据。科研与工作台分别维护焦点和近期安排；当前单个 `focus_task_id` 的兼容迁移须保留原关联。

列表显示任务 ID、名称、类别、科研位置或建设工作包、优先级、状态、依赖条件、执行计划和下一操作。人工指定的重点保留在列表；自动候选按就绪情况、优先级、计划日期及稳定 ID 排序。已完成和已取消任务进入历史，进行中与待验收任务分别提示继续实施或复核。

执行条件作为独立检查结果，不增加 `task.status` 的枚举值：

| 检查结果 | 展示与操作 |
|---|---|
| 依赖、交付及检查项齐备，计划版本已核对 | 显示就绪提示，可从任务节点打开主计划章节 |
| 前置依赖未满足或其验收证据失效 | 显示具体任务与原因，定位依赖 |
| 无主计划关联或文件缺失 | 显示「待关联主计划」或「计划文件缺失」 |
| 章节失效、文件变化或尚未核对 | 显示“计划待核对”，保留上次核对版本 |
| 类别或主归属待核对 | 显示待补项，引导修正 |

未通过检查的任务可保留在近期安排中，并展示具体缺项或阻塞原因。计划可定位时仍可查看，以便核对和修正。补齐管理信息不自动改变现有任务状态。

每项任务可引用多份方案，直接执行时明确一份主执行计划及对应章节。保存项目相对路径、章节定位、文件 SHA-256、核对人和核对时间。文件或章节变化时提示重新核对，不静默采用新内容；文件缺失时保留关联和历史。计划正文以实际 Markdown 文件为准，数据库只保存引用与核对记录。

从任务节点打开计划时复查实际文件和章节，定位当前内容并展示核对状态，参考计划通过任务详情查看。需要 Codex 执行时，在 Codex 会话中根据任务详情和项目计划组织指令。

### 4.4 文档、成果与问题

文档按“总体科研方案、系统设计、科研专项方案、科研执行计划、工作台建设方案、工作台执行计划、接口与数据契约、技术决策、验收记录、历史进度”分类，同时关联适用任务类别。参考文献继续进入资料与来源库。支持文档检索、Markdown 预览、章节定位及版本变化提示。

任务详情承载目标、实施范围、依赖、计划、交付物、检查项、关联问题/决策和历史。问题及决策注明影响类别；同一事项跨类别时关联已有对象，避免复制出两份不一致记录。

成果页区分软件交付、科研产物及验证范围。任务验收绑定标准版本与固定证据版本，展示证据缺失、变化或待复核。工作台验收通过不能提升科研证据分类，模型预测不能替代实验验证。

## 5. 任务状态与验收规则

### 5.1 执行状态

两类任务均沿用 `planned`、`ready`、`in_progress`、`in_review`、`done`、`blocked`、`cancelled`。现有 `workbench/service.py` 的状态转换及验收服务继续作为实现约束。

常规路径为 `planned → ready → in_progress → in_review → done`，后两步分别由提交验收与确认验收完成。另保留现有退回、阻塞、取消、恢复及重新打开规则；调用转换接口不能跳过验收直接写为 `done`。

| 操作 | 校验与记录 |
|---|---|
| 创建依赖 | 同项目对象存在，拒绝自依赖与循环依赖；跨类别依赖明确展示 |
| 就绪/开始 | 已填写交付物与验收项；前置任务完成且固定验收证据可用 |
| 提交验收 | 覆盖当前版本必需检查项，每项有证据或解释性记录 |
| 确认完成 | 必需项通过、证据可用，固定标准版本、结果、操作者与时间 |
| 阻塞/恢复 | 记录原因、恢复条件、处置结论，沿用现有转换限制 |
| 已完成任务扩大范围 | 保留旧验收，显式重开并更新标准版本 |
| 证据变化或失效 | 保留原验收，显示“已完成，证据需复核”，影响依赖就绪判断 |

第 4.3 节的计划核对是独立的交接检查。下一步工作与任务详情复用计划检测结果，任务状态及旧 API 的含义沿用现有契约。

### 5.2 科研证据与软件交付

保留“规划内容、已实现功能、已验证成果”三类研究证据及审查历史，与任务状态、运行状态分别管理。已完成的软件任务可说明功能实现；科研验证另需对应数据、方法、评价范围和领域复核。

核验记录明确软件产物核对、数据集来源接受、逐行原文核验或实验复核等范围。模型证据保留数据/特征/划分、目标与单位、指标及分母、适用范围；实验和反馈沿用既有领域契约。历史证据失效时标为待复核，不覆盖原结论。详细历史领域设计见 [v0.2 第 5.2 节](project_workbench_plan_v0.2.md#52-研发证据分类)。

## 6. 数据、版本与技术边界

### 6.1 权威来源

| 信息 | 权威来源 | 工作台职责 |
|---|---|---|
| 科研路线及方法 | 总体设计与专项方案 | 登记节点、保留来源章节与版本 |
| 任务类别、状态、依赖及近期安排 | `workbench.sqlite` | 统一维护，各页面读取同一服务 |
| 执行计划正文 | 项目 Markdown 文件 | 保存章节引用与已核对哈希 |
| 成果内容 | 实际数据、报告、模型及代码版本 | 索引固定版本与当前有效性 |
| 验收和管理决策 | 管理库记录及固定证据 | 保留历史和修订 |
| 科研数据 | 现有领域数据库及快照 | 本轮只读引用 |
| 进度文档 | 管理状态和证据的可阅读摘要 | 标注来源、导出时间；差异显式处理 |

不增加手工维护的 `tasks.yaml`、`roadmap.json` 等平行状态源；JSON 仅用于预览、初始化、交换或备份。文档写有“完成”及文件存在均不能自动触发任务验收。

### 6.2 增量数据设计

下表描述扩展对象的逻辑职责。WB-13 的实际存储与迁移结果见[增量迁移记录](../workbench/wb13_02_report.md)。

| 扩展 | 最小职责与约束 |
|---|---|
| 任务类别 | 任务独立记录科研/工作台类别；历史不明项待核对，阶段字段保持原义 |
| 路线节点 | 稳定 ID、项目、标题、阶段、父节点、排序、来源版本；拒绝父子环及跨项目关系 |
| 节点任务关联 | 明确主归属与引用，同任务同节点唯一；科研路线禁止直接挂入 WB 任务 |
| 计划引用与核对记录 | 任务、文档 ID/相对路径、章节、作用、主计划标志、已核对哈希、核对人与时间 |
| 分类焦点与近期安排 | 按任务类别保存焦点和近期任务 ID、人工排序；复用原任务身份 |
| 文档分类 | 复用已有文档索引补充用途分类和适用范围，不复制正文 |

依赖、验收、成果版本、问题、决策及活动复用现有对象。父子关系调整、任务分类、主归属、计划核对和近期安排均记录活动；修改携带预期修订号与请求 ID，在同一事务提交并处理重复请求及多标签页冲突。

### 6.3 文件访问、兼容与界面

文件读取校验工作区范围及解析后路径，Markdown 预览过滤不安全内容；沿用本机访问、写入来源与 CSRF 检查。管理库升级前通过 SQLite 备份接口备份，恢复后校验固定引用。索引失败保留最近成功结果及观察时间。

使用现有中文页面、分组侧栏、表格和状态标识；高频编辑逐步改为结构化表单。科研图形交互可引入轻量组件，无需整体前端重构。图中状态同时使用文字与颜色；桌面验收覆盖 1366×768、1920×1080，窄屏保留任务与计划入口。未实现能力明确显示待接入。
